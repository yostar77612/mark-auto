# Codex 作業規則：快、少來回、少重工

Status: ACCEPTED（擁有者 2026-11-01）。所有交給 Codex 的任務指令都要引用本文，並與
[M1 規格 0.1–0.3 節](m1-implementation-spec.md)（不過度防禦、能併行就併行、自主決策）一起適用。

## 為什麼要有這份規則

M1、M2 第一輪實測發現：慢的主因不是寫功能，而是**修基準釘選測試**（字串編號、檔案登記、
行號與雜湊釘選）、**子分支合併後重修釘選**、以及**每條分支各跑一遍完整測試**。
M2 第一輪的約 8 條分支共超過 400 個 commit，其中約三分之一是 `test(baseline)`、`pin`、
`register`、`measure` 類。以下規則專門削減這些成本。

## 規則

### R1 依「檔案區域」拆工作，不依功能拆

- 會碰同一批共用基準檔的工作放在**同一條分支**：字串目錄（`desktop_app/strings/*`）、
  `docs/analysis/08_REFACTOR_INVENTORY.md`、樣式表雜湊、頁面清單、`tools/layer_map.json`。
- 只有真正互不碰共用檔的工作才拆成平行分支。拆之前先列出每條分支預計新增的字串、檔案、
  樣式，確認沒有交集。
- 一個任務一個「整合負責分支」；子分支不各自重釘基準，見 R4。

### R2 每個任務指令都寫併行規則

- 每份指令開頭加上 [指令表頭](#指令表頭複製貼上) 的內容，等同引用 M1 規格 0.2 節。
- 驗證步驟能同時跑的就同時跑；推送後等 CI 時，立刻開始下一個沒被擋住的工作，不閒置、不輪詢。
- 例外：**不同時跑兩套完整測試**（會搶資源，造成時序測試失敗）。

### R3 完整測試交給 CI，本機只跑相關模組與啟動檢查

- 本機：只跑改動相關的測試模組、`compileall`、一次真實啟動檢查（LOCAL 與 BROKER_SIMULATION
  fake SDK 各一次，視窗要真的開起來）。
- 完整 `unittest discover` 由 CI 跑。CI 紅燈就依失敗清單修，不在本機重跑全套來「確認」。
- **例外，仍須在本機跑完整測試**：改到打包、安裝程式、`markauto.spec`、`build.ps1`、
  workflow、G3 相關檔案、分層規則（`layer_map.json`）時。
- 子分支一律不跑完整測試；只有整合分支在推送前跑**一次**。

### R4 基準更新集中做一次

- 功能開發期間不要每個 commit 都重釘基準。先讓功能與其專屬測試完成。
- 全部功能完成後，在整合分支用**一個** `test(baseline)` 系列 commit 一次登記：
  新字串編號、新檔案登記、樣式表雜湊、行號釘選、模組清單。
- 基準更新仍放在獨立 commit，commit 訊息逐項說明原因（既有規則不變）。
- 開工前就知道的新檔案與新字串，在介面 commit 一併預先登記，避免回頭補。

### R5 每輪設時間上限，超過就收斂

- 每個任務依規格排出估計時間；超過 **1.5 倍**仍有未完成項目時，把已完成且測試通過的部分
  收斂成可合併的最小範圍開 PR，其餘項目移到下一輪，在 PR 說明列出。
- 不為了「全部做完」讓已經能用的部分遲遲不能合併；能先給擁有者試用的先合併發布。

## 額外加速規則

### R6 基準修復工具化

- 寫一個 `tools/repin_baselines.py`（或同等工具）：一個指令掃描並重生所有可機械重生的基準
  （字串編號連續性、清單登記、樣式表雜湊、行號釘選），輸出差異摘要。
  開發者改完功能後跑它一次，不再手動逐檔修。
- 工具只**產生**基準更新，不降低任何斷言；產生結果仍須進獨立 commit 並說明原因。

### R7 釘選改成依符號，不依行號

- 以行號釘選（例如「repin expiry observer line」）的測試很脆弱，任何插行都會失敗。
  逐步改為依函式或類別名稱定位。這項是獨立的清理任務，不與功能混做。
- 改寫時不得削弱斷言：被保護的行為與原本相同，只是定位方式改變。

### R8 受影響測試自動選取

- 提供 `tools/affected_tests.py`：由改動檔案經 import 圖對應到需要跑的測試模組，
  作為 R3「本機只跑相關模組」的標準做法，避免漏跑，也避免全跑。
- 「無影響」不等於可跳過 CI；CI 的完整測試不變。

### R9 先清掉主線的舊紅燈

- `main` 目前有約 10 個失敗、27 個錯誤（Windows 主機限制）。每次驗證都要「跟 main 比對」就是
  因為它們還在。獨立清理：能修的修，確定因主機限制無法跑的，用明確的條件式略過並寫原因。
- 清完後，驗證標準簡化為「全綠」。

### R10 CI 加速

- 在 CI 把單元測試分片平行跑（matrix），縮短等待時間。
- 只改文件、不碰程式碼的 PR，不跑 Windows 安裝程式驗證（路徑過濾），但**改到打包、安裝程式、
  workflow 時一定要跑**。

### R11 指令要完整精確

- 給 Codex 的規格要預先列出：新增檔案、新增字串與編號、要碰的共用基準檔、驗收條件。
  含糊處由我們先決定，不讓 Codex 在實作中停下或猜測（呼應 0.3 節自主決策）。

## 不變的底線

快是靠重疊工作與減少重工，不是靠省略步驟。以下不因本文放寬：完整驗收條件、GitNexus impact 與
detect-changes、安全限制（LIVE 下單硬性關閉、G3 鎖定檔）、CI 全綠才合併、QA 獨立驗收。
